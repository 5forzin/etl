# Server agents

Agents are standalone Windows x64 and Linux x64 executables generated by the
Windows app. They need a public IPv4 address, an available inbound TCP port,
outbound HTTPS for IP detection, and access to the primary ETL controller.
They relay TCP and UDP using ETL v1 and v2. Clients connect directly to them;
the controller registers identities and tracks availability without relaying traffic.

## Generate and run

1. Update the primary Node server to a revision containing `src/agents.js`.
2. In the Windows app, choose **Servers → Add server**.
3. Set a name, platform and port. The default is 8443, which does not require root.
4. Choose **Generate file** and copy the resulting file to that server.
5. Allow that TCP port in the host and provider firewalls, then run the file.

Windows: open the generated `.exe` and keep its console running.

Linux:

```sh
chmod +x etl-agent-linux-x64
./etl-agent-linux-x64
```

Run within 24 hours of export. The executable contains a single-use pairing
code, the controller address and its public CA when configured. It never contains
the controller token or a private key. Generate a separate file for each server.
The first run creates that agent's own certificate, proxy token and device token.

The agent detects its public IPv4 through `https://api.ipify.org`. Override it
with `--public-ip ADDRESS` if the host has several public addresses. Before
accepting registration or an address change, the controller connects to the
public listener and verifies its TLS certificate and proxy credential.

The server appears in the app within about 15 seconds. Select it, then choose
Proxy only or Full mode and Connect. The primary and backup settings are retained.
Registration never changes an active client connection.

## State and lifecycle

Keep the agent running while using it. It does not install a service or modify
the firewall. Closing the console stops it; running the same file again reuses
its saved identity. Use the operating system's service manager for unattended startup.

Agent identities are stored in `%APPDATA%\ETL\agents\ID\state.json` on Windows
and `$XDG_CONFIG_HOME/ETL/agents/ID/state.json` on Linux (usually
`~/.config/ETL/agents/ID/state.json`). Linux directories and files use 0700 and 0600.
Keep this state private and retain it across restarts. Copying an already-paired
executable to a different machine does not transfer the identity or reuse the grant.

The controller stores state at `~/.local/share/etl/agents.json`, or at the path
specified with `--agent-state`. Docker Compose mounts a persistent `agent-state`
volume; the systemd unit uses `/var/lib/etl/agents.json`. Back up this file securely:
it includes proxy credentials and public certificates. Pairing and device secrets
are stored as hashes. The desktop caches proxy credentials using current-user DPAPI.

Heartbeats run every 20 seconds. A server is shown offline after 60 seconds
without a heartbeat. Removing a server revokes its device identity; a running
agent stops when its next heartbeat is rejected. If the controller is unreachable,
an already-paired agent continues serving its existing identity and retries.

Certificates last five years. Export a new agent when replacing an expired
certificate or a lost state file. `--version` prints the build version and
`--licenses` prints the bundled Go runtime license.

## Build and test

```sh
go -C agent vet ./...
go -C agent test -race ./...
go -C agent build -o ../build/etl-agent ./
```

Set `ETL_AGENT` to the built template and run `node --test test/agent-bundle.test.js`.
On Windows, also set `ETL_NATIVE_CLIENT` to exercise the native controller client
and resource exporter. Tests use isolated state directories and local TLS fixtures.
